## Available

- Python package and CLI commands: `doctor`, `validate`, `run`, `report`, and scoped `clean --run` / `clean --stale`.
- Strict YAML validation for one positive `create_order` operation in `orders_v1`/`standard_wallet`, concurrency one, at most five attempts, explicit bounded backoffs, and at most one response-suppression fault. All seven order invariants are required. Unknown fields and unsupported features fail validation.
- Real FastAPI/PostgreSQL order processing with deliberately unsafe and correct-A variants. Correct-A uses account-row locking, unique purchase/token constraints, and one transaction across all business effects. Conflicting payloads are rejected without new effects.
- A separate worker performs actual HTTP calls within private Docker networks. The coordinator suppresses the first matching successful response from the client policy and durably records that decision before retrying.
- A pure verifier reads complete snapshots from separate read-only PostgreSQL observation. It preserves duplicate rows and checks identity, atomicity, conservation, inventory, outbox intent, response consistency, and completion.
- Fresh isolated resources for every run/repetition, per-run labels and ownership nonce, resource limits, no published ports/host binds/socket mounts, read-only container filesystems with explicit ephemeral writable areas, bounded service logs, and cleanup in failure paths.
- JSON/Markdown reports, NDJSON event history, canonical snapshots, image identities, evidence hashes, offline integrity checking, and repeat outcome counts.
- Recovery of recorded resources after a coordinator hard kill, using the same output-root lock as direct engine execution. Entire cleanup selections are validated before mutation; separate versioned cleanup receipts preserve original evidence. Empty stale selections do not need Docker.
- Stage and total run deadlines, including a cleanup/reporting reserve, main-thread alarm interruption, partial attempt/fault retention, per-stage timing, and conservative timeout diagnostics. Cleanup timeouts preserve unresolved recorded IDs for later recovery.
- A checked internal order adapter: capability validation before Docker, domain preparation/readiness/quiescence/snapshot/verification hooks, strict snapshot envelopes, and complete versioned invariant-result checks. Missing/duplicate/malformed results and hook exceptions produce ERROR with a hook-specific diagnostic. No external registration yet.
- Adapter provenance in `adapter.json`, with package version and a bounded Python-source inventory hash; manifest/history/report references and existing artifact integrity checks. Validation exposes the built-in capabilities without Docker. Existing completed reports remain readable without adapter hooks.
- A maintained [learning guide](learning/README.md), with plain-language explanations, source/test maps, a glossary, and implementation decision records.

## Explicit milestone decisions

1. **Two internal networks, no proxy yet.** The client network connects worker/application; storage connects application/database/observer. Database connections go directly to the run-owned database. The four-network Toxiproxy topology in the v1 specification becomes necessary in Milestone 2. No database-network fault capability is advertised now.
2. **Built-in trusted environment.** There is no external project manifest or adapter loader yet. `--project`, arbitrary image/URL input, other domains, and additional service graphs are unsupported. The built-in runtime tag is resolved to its immutable local image ID before execution. The PostgreSQL image and Python base image are pinned by digest.
3. **Observation after graceful shutdown.** Work admission stops when the one logical operation finishes. The coordinator requests graceful application exit, then confirms zero application PostgreSQL sessions before treating the final state as quiescent. A forced kill or uncertain state produces UNKNOWN/INCONCLUSIVE. No restarted application or background worker can write afterward in this profile. The continuously running in-flight registry remains Milestone 2 work.
4. **Simple bounded helper protocol.** The HTTP worker starts once, acknowledges readiness, and receives correlated JSON requests over a persistent Docker exec stream. Python startup is outside attempt deadlines. Setup and snapshot helpers use bounded one-shot exec calls. The coordinator owns retry policy, fault application, event durability, and display order. This is not the concurrent event/acknowledgment protocol specified for Milestone 2. Worker timestamps are supplemental; different sources' monotonic clocks are not compared.
5. **Explicit time limits.** Request timeout 50–10000 ms, backoff 0–1000 ms, and at most five attempts. Stage budgets are positive and at most 300000 ms each; total is at most 900000 ms and must exceed reserved cleanup time. Defaults match the release's stage settings, including 60000 ms execution (previously 30000 ms when omitted). Initialization shares provisioning's deadline. The total timer begins after preflight/lock acquisition. Cleanup includes finalization and reserves up to one second for reporting. Linux main-thread alarms interrupt trusted coordinator code; a caller's active timer or non-main-thread execution is refused. Internal helper/database/readiness timeouts still impose shorter bounds where configured. Uninterruptible kernel/native operations can delay alarm handling; hard real-time guarantees, repeat-group and standalone recovery deadlines remain unsupported. Container memory is capped at 256 MiB each, one CPU each; database files are disposable tmpfs, so this does not test power-loss durability.
6. **Repetition is not replay.** `--repeat` reuses the validated plan and pinned current images with a fresh database each time. Strict historical replay, environment-difference comparisons, statistical reproduction groups, and reduction are not yet commands. No claim of deterministic OS scheduling is made.
7. **Fail closed and preserve evidence.** Corrupt or missing evidence is never presented as PASS. A full filesystem can prevent final report writing; the incomplete bundle remains diagnosable and ownership records support scoped cleanup. Artifact capture has a 50 MiB ceiling plus a small final diagnostic allowance. A configurable whole-group disk budget and broad secret sanitizers are later work; only synthetic bundled payloads are accepted now.
8. **Execution lock scope.** Every `run_one` call, including direct Python callers, and cleanup hold the same nonblocking OS lock within the selected output directory. Recovery holds it through manifest validation, deletion, and receipt writes. Each repeated trial locks separately; another command can enter between trials. Different output roots can run independently, protected by unique resource identities. The eventual workspace-wide coordinator lock is not claimed. Internal environment helpers are not a public execution API.
9. **Conservative stale recovery.** `clean --stale` considers at most 1,000 recorded run-directory entries, including completed runs. The lock establishes non-liveness; no age or PID inference is used. Recovery accepts only the current bundle/profile and up to six strictly validated resource records per 1 MiB manifest. The manifest's `execution_root` must match the resolved selected root, preventing copied bundles from bypassing the original lock. Legacy manifests without that field are refused for automatic cleanup; completed reports remain readable. Missing/malformed manifests, unexpected directory entries, and symlinked descendants refuse the selection before daemon mutation. Cleanup receipts live outside original bundles and do not revise their verdicts. A crash between Docker creation and persistence of the returned ID can leave an unrecorded resource; the tool refuses to discover/delete it by guessing. Whole-command recovery deadlines and guaranteed machine-crash durability remain deferred.
10. **Internal adapter bridge, not public v1 registration.** `boundary_version: 1` identifies the current bundled bridge, not compliance with the public API v1 specification. The parser, scheduler, images, and topology remain order-specific. Runtime hooks execute inside existing stage budgets; built-in description/input validation precede run timing. Quiescence still combines a strict graceful-exit boolean with independent session observation. Returned snapshots/findings are limited to one MiB and detached through canonical JSON. The source inventory covers this package's Python files (128 files, one MiB per file, four MiB total), not dependency packages or in-memory state; it does not enforce host/image equivalence or replay compatibility. See the [adapter guide](learning/adapters.md).

## Verification status

Latest adapter validation on 2026-10-23: 160 unit tests passed; all 13 Docker/PostgreSQL integration cases passed on the rebuilt runtime in 198.91 seconds. Ordinary unsafe/correct controls passed, the unsafe suppressed response produced the expected two-debit FAIL, and the corrected scenario passed with one debit. An intentionally incomplete adapter result produced ERROR despite a real correct purchase, with authoritative state retained and complete cleanup. The suite also reran isolation, payload conflict, interruption, hard-kill recovery, and all three deadline cases. No Faultline-owned containers or networks remained. See [adapter acceptance results](adapter-acceptance-results.md) for evidence and scope.

The earlier deadline phase had 107 unit tests, an eleven-case full Docker pass, and a final three-case targeted pass after a drain-boundary correction. Its measurements and image identities remain in [deadline acceptance results](deadline-acceptance-results.md).

The earlier recovery phase confirmed that cleanup refuses a live child run, removes its recorded leftovers after a hard kill, preserves original evidence, and leaves a separate environment usable. Its measurements remain in [recovery acceptance results](recovery-acceptance-results.md).

Across successive implementation phases, ordinary purchases passed 20/20 repetitions for each variant. After moving HTTP helper startup outside attempt deadlines, lost-response trials produced the expected duplicate-debit FAIL in 20/20 unsafe runs and PASS in 20/20 correct-A runs, all with required fault coverage. These are separate phase results, not one flawless eighty-trial run on the final revision. A stream close-order warning found during repetition was subsequently fixed and regression-tested.

The original rejected trial, corrections, environment, and evidence locations are documented in [acceptance results](acceptance-results.md). Do not treat example amounts or target counts in the specification as observed results.

## Next implementation boundary

Retain the defect, corrected scenario, adapter-contract errors, hard-kill recovery, and deadline behavior as regression cases. Next extend the internal adapter boundary into the strict project contract and separately packaged adapter integration, address creation-record recovery, and introduce the proxy topology. Add concurrent workloads and network faults only after their evidence and quiescence contracts are tested. React remains in M3; there is no placeholder frontend in this slice.
